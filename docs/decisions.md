### S-28 in detail
- **The login.** Until ticket #15 every request was `app_tenant`, so Postgres couldn't tell an admin from a tenant. Entering a restaurant gives the admin path power over onboarded restaurants, which is when this decision said to add a separate role. `app_admin` follows `app_tenant`'s rules: no superuser, no `BYPASSRLS`, owns no table, created by migration with no password, given one by `npm run db:migrate` from its own URL, and refused by `provisionAppRole` if RLS wouldn't apply to it. It can reach the `platform_*` functions and the `admin_auth_*` tables and no tenant table at all, and none of `app_tenant`, `app_admin` and `app_staff_auth` can become another. ESLint and a test keep `getAdminDb()` to the admin seam, which is `src/lib/tenant/platform-admin.ts`, `src/lib/tenant/admin-entry.ts` and the sign-in files that serve the admin audience. They keep `authDatabase()`, which hands back this login or staff sign-in's, to `src/lib/auth`.
- **Staff sign-in's login.** Until ticket #56 Better Auth's staff audience ran as `app_tenant`, so SQL run as `app_tenant` could clear `app.restaurant_id` and write a working magic link into `staff_auth_verification` for any staff member. `app_staff_auth` (`DATABASE_URL_STAFF_AUTH`, migration `staff_auth_database_login`) follows the same rules as `app_admin`. It can reach the `staff_auth_*` tables, including `staff_auth_code_limit`, and `staff_identity_by_email`, which is all sign-in needs, and no tenant or admin table. `app_tenant` holds no privilege on any `staff_auth_*` table. `end_staff_sessions` is a `SECURITY DEFINER` trigger, so deactivating someone or changing their email through `withTenant()` still ends their sessions with no grant to `app_tenant`. ESLint and a test keep `getStaffAuthDb()` to `src/lib/auth/database.ts` and `src/lib/auth/identity.ts`, and the tooling that runs outside a request.
- **`staff_identity_by_email` moved to `app_staff_auth` rather than being shared — proposed, not yet confirmed by Kudzai.** `app_tenant` can no longer run it, because `getTenantContext()` calls it right after reading the session through the same login, so nothing else needs it. Safe to build on, and to be confirmed before going live.
- **What stops a tenant identity.** (1) Postgres: `app_tenant` has no `EXECUTE` on any `platform_*` function, including `platform_admin_id_by_email`, and no privilege on any `admin_auth_*` table, so this holds whatever it does to `app.restaurant_id`. (2) `getPlatformAdminContext()` guards every admin route. (3) The functions refuse to run with `app.restaurant_id` set. (4) They need a real `platform_admins.id`, which is attribution and not authentication, because `audit_log` shows that id to the tenant. (5) The first-owner function refuses a restaurant that already has staff.
- **Three routes take a restaurant ID from request input.** A platform admin works across tenants and is choosing which one, so there's no session restaurant to take it from. `POST /api/admin/restaurants/[restaurantId]/owner` passes it only to `platform_create_first_owner`, `POST /api/admin/restaurants/[restaurantId]/enter` passes it only to `platform_enter_restaurant`, and `POST /api/admin/restaurants/[restaurantId]/qr-codes-printed` passes it only to `platform_set_qr_codes_printed` (S-33). All three sit behind `getPlatformAdminContext()`. After entering, the ID comes from the session like anyone else's.
- **Where the entered restaurant is held.** In `admin_auth_entry`, one row per admin session, written only by `platform_enter_restaurant` and `platform_leave_restaurant`, which `app_admin` can run and whose table it can only read. The browser holds nothing but its signed session cookie, so no cookie or parameter can choose the tenant. The row cascades from `admin_auth_session`, so signing out ends it, and an expired session reads as no session. A cascade can't audit, so a hook on the admin audience's sign-out leaves the restaurant first, before Better Auth deletes the session. It's per session, so an admin's other browser isn't inside. Under `DEV_AUTH_BYPASS` there is no real session, so the seed makes one for the same table to hang off, and switching identity stands in for signing out.
- **The shadow row is one per restaurant,** not one per admin: `staff_one_shadow_per_restaurant`, a partial unique index. That is what makes two first entries at once safe, and spec 00 asks for one. Which admin acted is `audit_log`'s job (S-29). `staff_shadow_row` holds it in Postgres to no email, which spec 00 asks for, and `role = owner`, which S-26 asks for. With no email it can't sign in, because sign-in finds people by email. Its display name is "Platform admin".
- **The shadow row is always active — proposed, not yet confirmed by Kudzai.** `staff_shadow_row` also requires `active`. Nothing asked for that: spec 00 shows it only because ticket #15 wrote it there. Safe to build on, and to be confirmed before going live.
- **An entered admin beats a staff session in the same browser — proposed, not yet confirmed by Kudzai.** An email can be both (S-30), and entering is a deliberate act, so `getTenantContext()` asks about it first. Leaving hands the browser back to the staff session. A request with no admin cookie pays nothing for this. Safe to build on, and to be confirmed before going live.
- **A restaurant can be entered before it has an owner, and its first staff record is still its owner (S-26).** Spec 01 puts no condition on entering, so `addStaff` holds the rule: with no active owner it takes only an owner, and the route answers a 409 for anyone else. That also keeps "Create owner" on `/admin` working, because the function behind it refuses a restaurant that already has staff. It's an app check and enough: only an entered admin can be there with no owner, and once there is one the last-owner trigger keeps it.
- **Inside a tenant the admin has no extra database power.** Its tenant queries run through `withTenant()` as `app_tenant`, under RLS. Only entering, leaving and reading the entry use `app_admin`.
- **Every admin action inside a tenant is audited, not just those on spec 01's list.** `recordAudit` takes the actor from the context, and `recordAdminAction` covers writes staff aren't audited for: settings saves (`restaurant.update`, with no values, because they hold the Wi-Fi password) and renames (`staff.rename`). Each entry and leaving is audited as `restaurant.enter` and `restaurant.leave`. Going straight to another restaurant counts as leaving the first, and so does signing out inside one, because signing out is someone acting. A session expiring on its own isn't audited, because no one acted.
- **Reads aren't audited — proposed, not yet confirmed by Kudzai.** Spec 01 and ticket #15 say every admin action, and this takes that to mean every write, so an admin can read a restaurant's Wi-Fi password and leave no record. Safe to build on, and to be confirmed before going live.
- **What doesn't hold.** All four URLs are in the same deployment. This stops SQL, not code: anything that can run code in the server process can read `DATABASE_URL_ADMIN`, `DATABASE_URL_STAFF_AUTH` and `DATABASE_URL_SYSTEM`. SQL run as `app_tenant` can still set `app.restaurant_id` to any tenant and read or change that tenant's data. What it can no longer do is create restaurants, read the list, learn who the admins are, get a platform-admin session, write `staff_auth_*` (so forge a sign-in for any staff member), or look an email up across tenants through `staff_identity_by_email`. It can still read the staff emails of any tenant it names, one tenant at a time. It can also still add an owner `staff` row, or repoint one, at an address it controls in any tenant it can name (slugs are public, and `restaurant_id_by_slug` turns one into an ID), then sign in legitimately as that owner. Closing that would mean moving staff writes off `app_tenant`. Code running arbitrary SQL as `app_admin` could do all the admin path can, attributed to any real admin id. Code running arbitrary SQL as `app_staff_auth` could plant a magic link for any active staff member, and so become an owner of any restaurant, and could learn who works where; it reaches no tenant data by itself.
- **The scheduled job's login, `app_system` (`DATABASE_URL_SYSTEM`, migration 0031, ticket #41) — proposed, not yet confirmed by Kudzai.** The most powerful of the four: it has `BYPASSRLS`, because the job acts across restaurants, so Postgres can't hold it to a tenant. Code running arbitrary SQL as it could read and change, within its grants, any restaurant's bookings. Safe to build on, and to be confirmed before going live. Its shape, which the ticket chose:
  - **Role shape.** `app_system` requires `BYPASSRLS` and refuses superuser, `CREATEROLE`, `CREATEDB`, `REPLICATION`, owning any table, and membership of any role. Migration creates it `NOLOGIN`; `npm run db:migrate` gives it a password and lets it log in from `DATABASE_URL_SYSTEM` and refuses to run without that variable (`provisionSystemRole`).
  - **Column grants, not table grants.** `bookings`: select `restaurant_id, id, table_id, status, starts_at, ends_at, hold_ends_at`, update `status, ends_at, hold_ends_at`. `booking_settings`: select `restaurant_id, buffer_minutes`. `audit_log`: insert on its seven columns, no update, no delete. `staff_auth_code_limit` and `admin_auth_code_limit`: select the window column and delete. Added by ticket #43 for D-06's purge (migrations `booking_phone_purge` and `booking_phone_set`): `bookings`: select `guest_phone_set` (a stored generated column, `guest_phone IS NOT NULL`) and update `guest_phone`, and `restaurants`: select `id` and `timezone` only (the booking date is the local date; the table also holds the Wi-Fi password and contact number). It can't read `guest_phone`: the purge finds its rows by `guest_phone_set`, and `UPDATE … SET guest_phone = NULL` needs no read of the column it writes. A column grant can't say "only to null", so a trigger, `bookings_system_phone_null_only`, refuses any non-null `guest_phone` written while `current_user` is `app_system`; without it, SQL run as this login could point any upcoming booking in any tenant at another number, and spec 05's messages would go there. No guest name, number or manage link is readable, it can write no booking column but `status`, `ends_at`, `hold_ends_at` and `guest_phone` (and that one only to null), and it has no `EXECUTE` on any `SECURITY DEFINER` function. **For Kudzai, the trade-off:** the first version of #43 granted select on `guest_phone` itself, which let this login read every guest's number across every tenant; the security review asked for the generated column instead, at the cost of one more column and a table rewrite when the migration runs. The read grant would be the simpler design if you'd rather; the trigger stays either way. `src/db/system-role.int.test.ts` pins these.
  - **Completion uses staff Finish's clamp at the job's now.** A seated party past `hold_ends_at` is completed with the same rule as Finish (spec 04): `ends_at` moves to the job's now and the hold is re-extended to now plus the buffer, capped at 960 minutes after the start and at the next booking's start on that table. Completion is audited as `booking.finish` with `actor_type = system`, the same action as staff's Finish, because `actor_type` already tells them apart. Spec 04's Audit bullet says so.
  - **Env choice.** `DATABASE_URL_SYSTEM` and `CRON_SECRET` stay optional in `src/lib/env.ts`, not production-only, which is an exception to "a ticket that depends on a variable makes it required". The production check also covers preview deployments, where a missing value would stop the whole site booting, while the route fails closed on its own (S-35). The cost: a production deploy with `CRON_SECRET` set and `DATABASE_URL_SYSTEM` missing answers 500 every 5 minutes until fixed.
  - **Booking rate-limit rows aren't swept by the job.** Spec 04's abuse controls said "and by the scheduled job when there is one"; the spec now defers that, because random sweeping on use keeps the table small and `app_system` has no grant on it. Sign-in code rows are pruned by the job (S-30).
  - **Before production.** Creating a `BYPASSRLS` role on Postgres 16+ needs the migrating role to hold `BYPASSRLS` itself. Not verified for Neon's owner role: try migration 0031 on a Neon branch first.

### S-30 in detail
- **Sign-in lookup.** `staff_identity_by_email(email)` and `platform_admin_id_by_email(email)` are the only way past RLS before a tenant is known. They take an exact email and return only what a session needs. Each pins `search_path` and has `EXECUTE` revoked from PUBLIC. `staff_identity_by_email` is granted only to `app_staff_auth`, and `platform_admin_id_by_email` only to `app_admin` (S-28). `DATABASE_URL_SYSTEM` stays for the scheduled job and the Meta webhook (spec 01). These are also what `getTenantContext()` calls on each request, so deactivation takes effect on the next one. That also replaces the transaction the dev path uses, keeping a request to two or three round trips. On a signed-in staff request the session read and this lookup go through `app_staff_auth` and the tenant queries through `app_tenant`: the same queries as when all of them were `app_tenant`, so still two or three round trips. What changed is connections. The request now checks a connection out of two pools where it used one, and a pool closes a connection left idle for 10 seconds (the driver's default `idleTimeoutMillis`). So a staff request that reaches an instance whose pools have been idle for more than 10 seconds opens one more connection than it did, not only on a cold start. This is read from the code, not measured.
- **Each login has its own pool, at the driver's default size — proposed, not yet confirmed by Kudzai.** That default is `max: 10`, so an instance that has opened all three pools (`app_tenant`, `app_admin` and `app_staff_auth`) can hold up to 30 connections to Postgres. Safe to build on, and to be confirmed before going live.
- **The same email at two restaurants can't happen.** `staff.email` is globally unique (spec 00), and now case-insensitively so, for `platform_admins` too. An email is one person at one restaurant, so sign-in never has to ask which one. Someone who works at two restaurants needs two addresses. An email can be both staff and a platform admin: they sign in to each separately.
- **Better Auth's tables** (`staff_auth_*`, `admin_auth_*`) have RLS with the reverse of the tenant policy: rows are visible only when no tenant is set. Better Auth's staff audience runs as `app_staff_auth` outside any tenant, and its admin audience as `app_admin`; nothing inside `withTenant()` can read or change a credential. On its own the policy is a boundary against bugs, not against SQL injection, which could clear the setting just as it could change `app.restaurant_id`. What stops that is that `app_tenant` holds no privilege on `staff_auth_*` or `admin_auth_*` at all (S-28).
- **What's stored.** Magic-link tokens and codes are stored hashed. Session tokens are stored raw, because Better Auth has no option otherwise, but the cookie also carries an HMAC made with `AUTH_SECRET`, so reading the table isn't enough to forge one. Writing is another matter: a magic link is only a row in `*_auth_verification`, so whoever can insert one can sign in as anyone that audience allows. Only `app_staff_auth` can write `staff_auth_verification`, and only `app_admin` `admin_auth_verification`; `app_tenant` can write neither (S-28). There is no password column, and Google's tokens aren't kept: Google is only asked who someone is. That means turning off Better Auth's schema check, which insists on those columns.
- **Separate sessions.** `/api/auth/staff/*` and `/api/auth/admin/*`. A session, link or code from one means nothing to the other. Only the sign-in endpoints we use are exposed; the rest of Better Auth answers 404.
- **Deactivation** ends sessions twice over: `getTenantContext()` refuses on the next request, and a trigger on `staff` deletes the sessions, so reactivating someone can't revive a forgotten tablet. Changing a staff email ends their sessions too.
- **CSRF.** Spec 01 requires SameSite=Lax. `src/proxy.ts` also refuses writes under `/api` whose `Origin` isn't this host. It costs one header comparison, covers every route with no caller changes, and catches what Lax doesn't: sibling subdomains are same-site, and this product serves files from a custom subdomain. A request with no `Origin` is let through, because browsers always send one on these requests and the Meta webhook never does.
- **Idle expiry.** Better Auth moves a session's expiry in the database as it's used, at most once a day, but a page can't set cookies, so `src/proxy.ts` re-sends the cookie with a fresh 30 days on staff paths.
- **The ceiling on codes.** Better Auth's limits don't stop a patient guesser: its 3 wrong tries are per code, every new code resets them, and its 3-a-minute limit is per IP. So each email gets **20 code attempts per 24 hours**, per session type. Sending a code spends one and trying one spends one, up front, so parallel guesses can't slip past. The window starts at the first attempt and refused attempts don't extend it. A code that works clears the count. Past the ceiling the send and sign-in endpoints answer 429 `sign_in_codes_paused`, and the form points at the other ways in. Magic links and Google aren't touched. **Why 20:** one send plus its 3 guesses costs 4, so an attacker gets 15 guesses a day against 1,000,000 codes, however many IPs they own. That's about 0.045% a month and 0.5% a year against one named person, down from about 14% a month from one IP and even odds in 4 hours from 1,000. Staff sign in about once a month, because sessions last 30 days, so 20 leaves room for typos and lost emails. The cost: anyone can pause codes for an email for a day with 20 requests, which is why the link and Google must stay outside it. Everyone is counted the same whether they're known or not, so a refusal says nothing about who works where, and the tables hold every address tried, as `*_auth_verification` already does. **Where:** `staff_auth_code_limit` and `admin_auth_code_limit`, because memory would be per-instance on Vercel, and not `*_auth_rate_limit`, which Better Auth prunes down to its own longest window of about a minute. It runs in every environment, unlike the per-IP limiter, so tests exercise it. To lift a lockout, delete the email's row. **Retention:** a row past its 24-hour window has no further use, because the next attempt starts a fresh one. Rows are keyed by whatever address someone typed, strangers' included, and are deleted today only by a successful code sign-in. The 5-minute scheduled job prunes them (S-35, issue 41: `src/lib/cron/code-limits.ts`), with the same test the ceiling uses for a window being over. Between runs, growth is bounded by the per-IP limiter and by the hook keeping a row only for a string that could be an address: at most 254 characters, containing an `@`.
- **Refusals on pages.** Spec 01's 401 and 403 are HTTP statuses on route handlers. Pages stream, so the status is already sent as 200 by the time a refusal is thrown, and a refused page shows the refusal with no data and `noindex`. The tests of a screen therefore prove `forbidden()` or `unauthorized()` is raised before any data renders, not the status on the wire.
- **Sign-ins aren't audited.** Spec 01's audit list doesn't include them.

### S-32 in detail
`/m/{menu_token}` is a Route Handler that writes its own HTML, not a Next.js page. Ticket #19.

**Why.** An App Router page can't leave out the framework: a `page.tsx` with no client components still shipped 8 scripts, over 170KB gzipped, on this build. That breaks spec 02's budget (under 100KB, no client JS without a reason) before the menu is added. A Route Handler ships no JavaScript. A Pages Router page might not have this problem, but it wasn't tried, and it would be a second router for one page. That attempt also answered an unknown token with a 200, but that came from how it was written: `notFound()` before anything streams gives a real 404, so it's no reason to avoid a page. *(Proposed, ticket #32.)* That doesn't hold for a page with a dynamic param under this build's Cache Components: `/r/{slug}/book` serves an empty shell with its 200 before the page runs, so `notFound()` gives the not-found page with `noindex` and a 200. There is no per-route way out. The booking page accepts that rather than become another exception to the stack.

**What this decides.** Spec 01 and D-07 decide on Next.js App Router, Tailwind and shadcn/ui. This page uses none of React, Tailwind or shadcn/ui, so its markup and styles are separate from the staff side's. A public page that really needs client-side behaviour would have to bring its own small script, which is the budget's point.

**A second Route Handler — proposed, not yet confirmed by Kudzai.** `/b/{manage_token}` (ticket #34) also writes its own HTML with no React, Tailwind or shadcn/ui, so the menu is no longer "the one exception" the decision names. It has the menu's reasons, and it needs a real 404 and headers of its own, which a page can't give it on this build. Spec 01 says so too. Safe to build on, and to be confirmed before going live.

**What it rests on:**
- **The budget.** Spec 02 calls 100KB a proposed number. A much higher one would take away the main reason for this.
- **Phase 6, settled 2026-11-11 (ticket #49).** `/t/{qr_token}` shows this menu in phases 3 to 5, and copies this route in chain 3. In phase 6 it becomes the ordering entry point (spec 06), which needs client-side behaviour, and a path can't have both a `route.js` and a `page.js`. The options were to replace the route with a page, which pays the framework's scripts on the table QR, to add a small script of its own to the hand-written page, or to move ordering to a second URL. **Decided: the second.** `/t/{qr_token}` stays this Route Handler, and ordering adds one small standalone script to it for the cart, the customer's name and the order tracker, inside spec 02's budget. *(Proposed: the menu HTML stays cached as it is now; the script talks to uncached endpoints of its own, so nothing per-session is ever written into the cached page.)* `/m/{menu_token}` gets no script and never takes an order (spec 03).

**How it's built:**
- **What the page is.** `src/lib/public-menu.ts` writes it with the `html` template tag (`src/lib/html.ts`), which escapes everything put into it. `react-dom/server` can't be used, because Next.js refuses it in a Route Handler. One inline stylesheet, no web fonts and no root layout, so the whole page is one response: about 1KB for one item, and a test holds a 30-item menu under budget.
- **How it caches.** `generateStaticParams` is what makes this work: with it, the first visit to any token stores the response like a prerendered page, with `s-maxage`, and later visits are served from that store. Without it the handler runs on every request. Cache Components insists on at least one sample and the build has no database, so `BUILD_SAMPLE_TOKEN` answers a 404 without one. Everything the token leads to, the lookup included, sits inside one `use cache` function, because uncached database access would make the response dynamic.
- **Revalidation on save.** The tag is the restaurant's (`menuTag`), so a save refreshes that restaurant's URLs and no other, whichever token they use. It uses `{ expire: 0 }`, not the recommended `"max"`: `"max"` would give the next customer the old page while the new one renders, and a price mustn't be out of date once someone has saved it. The cost is one blocking render per save. Anything the page shows has to call `revalidateMenu()` once committed, which is why restaurant settings do too: the page shows the name.
- **Revalidation every 5 minutes.** A found page has `cacheLife({ revalidate: 300, expire: 300 })`, which sends `s-maxage=300`. Issues 3 and 24 need this, so that a special starts or ends within 5 minutes of its window without a save. It also bounds a race: a render overlapping a save can store the old page after the tag has expired, and that page then counts as fresh, for at most these 5 minutes. `expire` matches `revalidate` to make 5 minutes a ceiling. With a longer `expire`, the first visit after a quiet spell would get the old page and only start a refresh. The cost is that a visit after the 5 minutes waits for a render instead, once per URL. Next.js treats an `expire` under 5 minutes as dynamic, so this is also as short as it can go. An unknown token gets `cacheLife("minutes")`, since it has no restaurant, and so no tag to revalidate it by.
- **Only GET and HEAD reach the cache.** Next.js fills this cache by path, whatever the method. On a production build, one anonymous POST, PUT, PATCH or DELETE to a page not in the cache stored an empty 405 as that page, with a year's `s-maxage` and no tag, so a save couldn't clear it. An unrecognised method stored a 400 the same way, and an OPTIONS left every later visit hanging. Exporting handlers for those methods doesn't help: it stops the route caching at all. So `src/proxy.ts` answers anything else under `/m/` with a 405 before it gets there. A new public page adds its prefix to `publicPagePrefixes`, its path to the matcher, and an entry in `test/production/public-pages.test.ts`.
- **What the proxy costs.** It runs ahead of the cache, on every visit, including one the cache would answer. The matcher can't filter on method, so that can't be narrowed. Next.js's proxy runs on Node.js, so on Vercel each menu scan is one Routing Middleware invocation, billed, and the customer waits for it ahead of the CDN. That wait hasn't been measured on Vercel, and it's the number to check before going live. On `next start` it's lost in the noise: a cached visit took 0.44ms with it and 0.45 to 0.50ms without, over 2,000 visits each, which says nothing about Vercel's network. Nothing is added to the page, and a public path does a method check and nothing else: no cookies, no session, no database. Whether Vercel's own cache can be poisoned this way hasn't been tested either. Vercel's CDN doesn't cache a POST, so the proxy may turn out to be needed only off Vercel, but that has to be shown on a deployment before it's taken away.
- **The public path doesn't load sign-in.** `withTenant()` lives in `src/lib/tenant/scope.ts`, and `src/lib/tenant/index.ts` re-exports it alongside the identity code that imports Better Auth. Code on a public route imports `./scope` and `./public`, never `@/lib/tenant`. `src/lib/tenant/public-path.test.ts` fails if the route reaches Better Auth by any path.
- **How it's checked.** `use cache` and the proxy don't run under the ordinary tests, so `npm run test:production` runs `next start` on a production build, in CI as well: miss then hit, the `s-maxage`, each refused method followed by a customer's visit, a 404 for an unknown token, and a save refreshing one restaurant and not another. That's Next.js's own cache, not Vercel's.

### S-36 in detail
D-01 asked how to stop someone who photographs a table's QR code from ordering from anywhere. Kudzai's ruling, 2026-11-11, ticket #49.

**What this decides.**
- The QR token is all a customer needs. The first scan of a table with no open session opens one, later scans join it, and an order goes straight to the kitchen (spec 06).
- Nothing checks where the customer is. There is no staff approval of a new session, no per-table code, and no Wi-Fi, IP or location check.
- The human override is staff's. Staff see every order as it arrives, with its table and customer name, on the kitchen board and the floor view. If an order looks wrong, for example a table with nobody at it, staff **reject** it, which voids its items, or **void** single items. Either needs a reason, and both are recorded with the staff member and audited (spec 01). Owner and staff can both do it, as with any void (S-26).
- A reject voids every item of the order that hasn't been delivered. *(Proposed: a delivered item was carried to a real table, so it stays.)* The order then leaves the kitchen board.

**Why.** Options 1 and 2 put a step in front of every party: one waits for a staff tap, the other types a code. This keeps ordering as hands-off as booking is, with a human override (docs/README.md › Product principles), and payment still happens at the table with the waiter, so a fake order costs food and the kitchen's time, not anyone's money.

**The accepted risk.** A photographed QR code can place orders, from anywhere, until staff notice and reject them. Regenerating the table's token (spec 03) stops that code for good.

**What changes in the specs.**
- Spec 06's acceptance line "Whatever D-01 decides has an automated test showing a remote order can't reach the kitchen" no longer fits: under this decision a remote order does reach the kitchen. It now asks for what the decision promises instead: a staff reject voids every item of the order (undelivered items only, *proposed*, see S-36 in detail), recorded with the staff member and reason, and the order leaves the kitchen board.
- `table_sessions.approved_at` is unused in v1. It stays in spec 00 rather than being dropped, so option 1 can still be added later without a schema change if real service shows it's needed. Nothing writes or reads it.

**Also ruled the same day.** Spec 06 and 07's proposed items ("Call a waiter", the kitchen's ageing at 15 and 25 minutes, polling every 5 seconds) are built as written, and stay marked proposed. How `/t/{qr_token}` takes ordering is settled in S-32.

### S-40 in detail
How the ordering tracer (ticket #69) builds what spec 06 and S-32 leave open. All of it is *proposed, not yet confirmed by Kudzai*, and safe to build on.

- **The endpoints.** The proxy refuses every method but GET and HEAD under `/t/`, for the cache's sake (S-32), so the page's writes live under `/api/t/{qr_token}/`: `session` (a scan) and `orders`. Both are uncached (`no-store`), find their tenant through `resolvePublicToken("table", …)` (S-31) and then the table by its token inside the tenant, so an archived or regenerated table's token opens nothing and orders nothing (404). Neither loads sign-in (S-32). The proxy's cross-site check covers them, as it does every `/api` write.
- **Opening or joining is one statement.** `INSERT … ON CONFLICT (table_id) WHERE status = 'open' DO UPDATE SET last_activity_at = now()`: two phones scanning a free table at once meet on the table lock, and the second waits for the first, then joins its session rather than failing.
- **The session the page joined is a precondition, not a key.** The order endpoint finds the table's open session by the token, and refuses the order (409, `session_changed`, nothing written) unless it is the session the page says it joined. A stale tab can't order into a new party's session, and naming another session reaches nothing. The page then joins again and the customer places the order again. The issue's "never a session id from the client" is read as "never used to choose where an order goes".
- **Order rate limit.** At most 10 orders per table session in any 5 minutes; past it a 429 with `Retry-After`, and nothing is written. Counted in the order's own transaction after taking the session's row, so parallel orders queue and can't all pass. No limit was decided; the run's orchestrator chose this, since a photographed code could otherwise flood a kitchen. Spec 04's booking limit is per address because it has no session; this one is per session because ordering has one.
- **Limits.** A customer name up to 100 characters (like `guest_name`), a note up to 200, a quantity 1 to 20, all as CHECKs as well as in the endpoint (400). A blank note is refused by the CHECK; the endpoint stores a blank note as null rather than refusing the order.
- **Pieces of #70 built here.** The page's script already remembers the customer's name on the phone, per session (keyed by the session, so the next party at the table starts blank), shows "Pay at the table with your waiter as usual" once an order is placed, and has the per-item note input. They landed in #69 and #70 builds on them.
- **The script.** Inline in the cached page (one response, measured whole by the budget test, and never out of step with the endpoints it calls), plain DOM, about 2KB. It reads the token from the address. Add buttons are in the page but hidden until the scan has succeeded, so without JavaScript the page is the plain menu. The item's id is on the table's page, which the generic menu never shows.
- **Frozen prices.** A line's `unit_price_usd` and `unit_price_zig` are nullable: null is a currency that couldn't be worked out when it was ordered (no rate yet), as the menu showed it. A ZiG price says whether it was fixed or calculated, and a null one has no source: `CHECK ((unit_price_zig IS NULL) = (zig_source IS NULL))`. The frozen-column triggers also hold the bill a row is on: `order_items_frozen` refuses a change to a line's `order_id`, and `orders_frozen` to an order's `session_id` (with `rate_used`), whoever asks. The open-session triggers fire on insert only, so without this a later staff path could move a priced line or a whole order onto another bill, a closed one included. A trigger rather than a REVOKE, so it binds the owner role too, like the other frozen columns.
- **No hard deletes.** app_tenant has no DELETE on `table_sessions`, `orders` or `order_items`: nothing customer-facing is hard-deleted (spec 00), and a void is a status.
- **The kitchen list.** `/dashboard/kitchen` (D-10) shows placed items, oldest first, with no times on it yet, so no timezone question arises until the board shows ages (#71).

### Abuse controls on the guest's confirm — **proposed, not yet confirmed by Kudzai**
Spec 04's abuse controls (ticket #33), with the calls the spec left open. Detail is in spec 04 › Abuse controls.
- **Rate-limit storage:** Postgres (`booking_rate_limit`), not memory or a new service. Hashed key, 5 per 10 minutes, per visitor.
- **Which address:** `x-vercel-forwarded-for` on Vercel only. Missing in production: one shared count (fails closed). Missing in development: no limit.
- **Per-phone limit:** a trigger with an advisory lock, because counting then inserting is a race.
- **Bot check:** fails closed in production and preview deployments with no secret; fails open in every environment only when the guest has a token and siteverify can't answer. A full Cloudflare outage still stops online bookings: the widget loads from the same host, so there is no token and the guest gets a 403.

## Open

### D-01: Fake remote QR orders — **resolved 2026-11-11, see S-36**
Someone could photograph a table's QR code and place orders from anywhere. The options were:
1. **Staff approve new sessions.** The first order at a table pings staff to accept. Anyone joining an already-approved session isn't asked. That costs one tap per table, not one per order.
2. **Per-table code.** Customers enter a short code shown at the table. No staff tap, but every party has to type it.
3. **Both, chosen per restaurant.** The most flexible option, and the most to build and test.

The recommendation was option 1. **Decided instead:** neither. The QR token alone lets a customer order, and staff reject or void suspicious orders with a logged reason (S-36).

### D-02: Large parties and combined tables
v1 assigns exactly one table per booking. Parties larger than the biggest bookable table, or larger than `max_online_party_size`, see a "contact the restaurant" message instead. Revisit this if venues regularly push tables together for groups.

### D-03: Reminder timing
Proposed: one reminder 3 hours before the booking, skipped if the booking was made less than 3 hours ahead. An alternative is a day-before reminder plus a same-day one. That costs more per booking in Meta template fees.

### D-04: Recurring specials ("every Tuesday 5–9pm")

### D-05: Overlapping specials on one item
Proposed: the database rejects a second active special that overlaps on the same item.

Built in ticket #24 (2.6) as the exclusion constraint `specials_no_overlap`, still proposed until Kudzai confirms it. Details in spec 00 (specials): it is per restaurant and item, ignores specials that are off, treats a missing start or end as unbounded (the form stores a blank start as the moment of saving, so a special that is over never blocks a new one with a blank start; turning a special on switches off that item's other active specials whose end has passed, in the same transaction, so one that is over never blocks a turn-on either, and a refusal leaves them as they were), and lets specials that meet at midnight sit side by side. If this is rejected, drop the constraint in a migration and the app's 409 answer goes with it.

### D-06: Guest phone number retention
A booking needs a WhatsApp number. Proposed: null the number 30 days after the booking date, keeping only the name and the booking outcome for no-show stats.

Built in ticket #43 (4.14), still proposed until Kudzai confirms it. The job's `phonesPurged` task (`src/lib/cron/phone-purge.ts`, S-35) nulls `bookings.guest_phone` at the local midnight that starts day *booking date + 30*, where the booking date is `starts_at` as a calendar date in `restaurants.timezone` (never UTC, never the server's zone). So a booking on 2 May loses its number at 00:00 on 1 June, restaurant time. It goes by the booking whatever its status, because a cancelled booking's number is as personal as a completed one's and nothing is sent for a booking that old. It writes only `guest_phone`: the name, status, party, note and the rest stay, so the no-show metrics are unchanged. It isn't audited (it is retention housekeeping, like S-30's pruning, and a batch of 200, up to 25 batches a run, would only add noise). The job never reads the number: it finds the rows by `guest_phone_set`, a stored generated column with a partial index on `starts_at`, and a trigger lets it write only null to `guest_phone` (S-28 in detail has the grants and why the generated column was chosen over reading the number). If this is rejected, remove the task from `tickTasks`, and the grants, trigger, index and column in migrations `booking_phone_purge` and `booking_phone_set` with it.
